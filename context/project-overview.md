# Техническое задание

## Telegram-система приёма и обработки заявок на ремонт (электрика/сантехника/прочее)

### 1. Цель проекта

Разработать Telegram-бота, автоматизирующего приём заявок от клиентов на ремонтные работы (электрика, сантехника, прочие бытовые услуги) и их распределение между сотрудниками по профилю услуги, с хранением данных в Google Таблице.

### 2. Роли пользователей

- **Клиент** — оставляет заявку через Telegram-бота.
- **Сотрудник** — специалист, закреплённый за одной категорией услуг (электрика / сантехника / прочее). Получает заявки своей категории, берёт их в работу и меняет статус.
- **Администратор (руководитель)** — доступ к Google Таблице со всеми заявками; управляет списком сотрудников и их категориями.

### 3. Сценарий работы

**3.1. Клиент**

1. Открывает бота, нажимает «Оставить заявку».
2. Выбирает категорию: «Электрика» / «Сантехника» / «Другое».
3. Указывает имя заказчика согласно договору, описание проблемы, город, адрес, срок исполнения и контактный телефон.
4. Получает от бота подтверждение с номером заявки.
5. Далее автоматически получает уведомления от бота при каждой смене статуса его заявки (см. п.5).

**3.2. Сотрудник**

1. Заранее закреплён администратором за одной категорией (электрика/сантехника/прочее) — соответствие «Telegram ID сотрудника → категория» хранится в отдельном листе Google Таблицы.
2. При появлении новой заявки своей категории уведомление получают **все** активные сотрудники этой категории одновременно, с деталями заявки и кнопкой «Взять в работу».
3. Заявку получает тот сотрудник, кто **первым** нажал «Взять в работу». Остальным сотрудникам бот сообщает, что заявка уже взята в работу коллегой (кнопка становится неактивной / приходит уведомление).
4. По приезде на объект сотрудник нажимает «Выехал на место» → статус меняется.
5. После завершения работ нажимает «Закрыть заявку» → статус меняется, заявка считается выполненной.
6. Если сотрудник не может выполнить взятую заявку, он нажимает «Отказаться от заявки»: статус возвращается к «Получена от клиента», заявка снова уходит всем сотрудникам категории, а сам отказавшийся сотрудник исключается из повторной рассылки по этой заявке.

Каждую заявку может менять статус только сотрудник, который её взял в работу (кроме отказа, который возвращает заявку в общий пул).
Лимита на количество одновременных заявок у одного сотрудника нет.
Отмена заявки клиентом не предусмотрена.

### 4. Статусы заявки

1. «Получена от клиента» — присваивается автоматически при создании.
2. «Взята в работу» — сотрудник нажал соответствующую кнопку.
3. «Выехал на место» — сотрудник нажал соответствующую кнопку.
4. «Закрыта» — сотрудник завершил работу.

### 5. Уведомления

- Клиенту: бот присылает сообщение при каждой смене статуса его заявки («Ваша заявка взята в работу», «Мастер выехал», «Заявка закрыта»).
- Сотрудникам: бот присылает сообщение о новой заявке в закреплённой за ними категории.

### 6. Хранение данных — Google Таблица

Единая база данных — Google Sheets, подключённая через Google Apps Script/API.

**Лист «Заявки»** (примерная структура столбцов):

- ID заявки
- Дата и время создания
- Telegram ID / имя клиента
- Клиент
- Телефон клиента
- Категория (электрика/сантехника/прочее)
- Описание проблемы
- Адрес
- Срок исполнения
- Статус
- Сотрудник, взявший заявку
- Дата/время взятия в работу
- Дата/время выезда
- Дата/время закрытия

**Лист «Сотрудники»**:

- Telegram ID
- Имя
- Категория (электрика/сантехника/прочее)
- Активен (да/нет)

**Лист «Database»**:

- Город
- Список категорий
- Код категории
- Количество заявок

**Лист «Оплата та розрахунки»**:

- ID заявки

### 7. Нефункциональные требования

- Максимальная простота интерфейса для клиента и сотрудника (минимум шагов, кнопки вместо свободного ввода где возможно).
- Масштабируемость: возможность в будущем добавить новые категории услуг и сотрудников без переписывания логики (достаточно новой строки в листе «Сотрудники»).
- Минимальная потребность в техподдержке: логика бота должна быть устойчива к ошибкам ввода, без необходимости регулярного вмешательства администратора.
- Логирование ошибок (например, в отдельный лист/чат администратора) на случай сбоев записи в таблицу.

### 8. Приложение: предлагаемая техническая реализация

Раздел носит рекомендательный характер — разработчик может предложить свой вариант, если он не противоречит требованиям п.7.

**Стек**

- Telegram Bot API: Node.js (`telegraf`). Один бот обслуживает и клиентов, и сотрудников — логика определяется по Telegram ID отправителя.
- База данных — Google Sheets, напрямую через Google Sheets API с сервисным аккаунтом.
- Хостинг: serverless-платформа (Google Cloud Functions/Vercel и т.п.) — чтобы не платить за постоянно работающий сервер при небольшой нагрузке.

**Поток данных**

1. Соответствие «Telegram ID сотрудника → категория» бот кэширует на несколько минут, подтягивая из листа «Сотрудники», чтобы не обращаться к таблице на каждое сообщение.
2. Диалог с клиентом строится на inline-кнопках и машине состояний (FSM — штатный механизм в aiogram/telegraf), а не на разборе свободного текста — так надёжнее.
3. По завершении диалога бот добавляет строку в лист «Заявки» и рассылает уведомление всем активным сотрудникам нужной категории с кнопкой «Взять в работу».
4. Разбор гонки при одновременном нажатии кнопки несколькими сотрудниками: бот при нажатии сначала проверяет текущий статус заявки в таблице — если он ещё «Получена от клиента», обновляет статус и закрепляет заявку за нажавшим; если уже занята — отвечает, что заявка уже взята коллегой. При текущих объёмах заявок (десятки в день) риск гонки минимален; при необходимости более строгой защиты можно добавить lock-флаг в отдельной ячейке.
5. Кнопки «Выехал», «Закрыть», «Отказаться» меняют статус конкретной строки по ID заявки и одновременно триггерят уведомление клиенту.

**Почему Google Sheets, а не полноценная СУБД**
При текущем объёме заявок это оправдано: не требуется сервер БД, руководитель может сам открыть таблицу и посмотреть или поправить данные вручную — это соответствует требованию минимальной техподдержки. Логика бота не привязана жёстко к Sheets: при росте нагрузки слой хранения можно заменить на Postgres/Airtable без переписывания сценариев диалогов.

**Примерные этапы разработки**

1. Настройка бота, диалог клиента (FSM), запись заявки в таблицу.
2. Логика сотрудников: рассылка заявок по категории, взятие в работу, смена статусов, отказ.
3. Уведомления клиенту о смене статуса.
4. Тестирование гонок при одновременном взятии заявки, обработка сбоев записи в таблицу, логирование ошибок.

### 9. Вне рамок текущего ТЗ (не реализуется на этом этапе)

- Оплата и выставление счетов через бота.
- Геолокация/карта сотрудников.
- Мобильное приложение и веб-панель — весь функционал реализуется через Telegram-бота.
- Автоматическое распределение заявки между несколькими сотрудниками одной категории (заявку берёт тот, кто первым нажал «Взять в работу»).
